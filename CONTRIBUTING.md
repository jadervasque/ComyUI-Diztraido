# Contributing

Contributions are welcome when they preserve workflow compatibility and maintain the separation between nodes, services, routes, and frontend code.

## Before you begin

- Search for an existing issue to avoid duplicated work.
- For broad or incompatible changes, open a proposal first and describe the motivation, impact, and migration strategy.
- Do not include models, private images, outputs, credentials, or files generated by ComfyUI.

## Reporting bugs

Use the bug report form and include:

- the ComfyUI version or commit;
- the operating system and Python version;
- minimal reproduction steps;
- expected and observed behavior;
- relevant logs without personal data;
- a minimal workflow when it can be shared safely.

Vulnerabilities must not be reported in public issues. See `SECURITY.md`.

## Proposing features

Explain:

- the problem the feature solves;
- the expected behavior;
- the impact on existing nodes and workflows;
- the alternatives considered;
- whether backend, frontend, or both require changes.

## Development workflow

1. Create a branch from `master`.
2. Make small and focused changes.
3. Add or update tests.
4. Update the corresponding documentation in English, Brazilian Portuguese, and Spanish.
5. Run:

```bash
python -m pip install -r requirements-test.txt
python -m compileall -q .
python -m unittest discover -s tests -v
```

6. Open a pull request using the repository template.

## Implementation standards

- One node per file in `nodes/`.
- Reusable rules in `services/`.
- Central registration in `nodes/__init__.py`.
- Route registration centralized through `routes/__init__.py`.
- Visual extensions in `web/`.
- Tests in `tests/`.
- Type hints and concise docstrings in reusable Python code.
- Preserve node IDs, inputs, and outputs unless an approved migration is included.

See `docs/ARCHITECTURE.md` and `docs/DEVELOPMENT.md` for details.

## Commits

Use concise imperative messages or Conventional Commits:

- `feat: add a new node`
- `fix: restore widget state`
- `docs: update installation guide`
- `test: cover reference chaining`
- `refactor: extract rule into service`
- `chore: update automation`

## Pull requests

A pull request must:

- explain the problem and the solution;
- remain limited to one primary objective;
- describe compatibility impacts;
- include validation evidence;
- update tests and documentation;
- avoid files unrelated to the stated scope.

Approval is not guaranteed. Changes may require adjustments to preserve compatibility with ComfyUI and saved workflows.
